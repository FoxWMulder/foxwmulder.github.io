Включить Long Paths в Windows (это обязательно для полной поддержки >260 в 2025–2026 году):  
  
- Win + R → regedit  
- Иди в HKEYLOCALMACHINE\SYSTEM\CurrentControlSet\Control\FileSystem  
- Создай/измени DWORD (32-bit) параметр **LongPathsEnabled** → значение **1**  
- Перезагрузи комп (или хотя бы explorer.exe). После этого **многие** приложения начнут понимать длинные пути (если они сами long-path-aware).  
  
---  
  
- Если ты получаешь путь из **Windows API** без поддержки long paths (без \?\ префикса и без LongPathsEnabled=1 в реестре) → строка обрезается на **~260 символах** (MAXPATH).  
- Если у тебя **LongPathsEnabled** включён (HKEYLOCALMACHINE\SYSTEM\CurrentControlSet\Control\FileSystem → LongPathsEnabled = 1) и приложение **long-path-aware** (в манифесте <longPathAware>true</longPathAware> для новых Delphi) → Delphi может получить пути до **~32 767 символов** (NTFS лимит).  
- ExtractFileExt спокойно обработает и такой **32k-символьный** путь — просто вернёт расширение из конца строки.  
    
---  
  
### Почему именно последний символ (x → ничего, .mebx → .meb)?  
  
- NTFS всегда хранит **два имени** для каждого файла: длинное (LFN) и короткое 8.3 (если включено).  
- Короткое имя генерируется как **первые 6 символов имени + ~1 + первые 3 символа расширения**.  
- Для файла вроде оченьдлинноеимяфайла.mebx короткое может стать примерно OCHEN~1.MEB (расширение обрезается до 3 букв: .meb).  
- Когда твой код (или Shell/API, которые использует Delphi по умолчанию) **не** передаёт путь с префиксом \\?\ и не является long-path-aware → Windows **возвращает короткое имя** вместо длинного.  
- В результате ExtractFileExt (или что ты там используешь для получения расширения) получает строку с коротким именем → .meb вместо .mebx.  
- Последний символ "x" пропадает именно потому, что в 8.3 расширение **всегда** max 3 символа.  
    
---  
    
Если из FindFirst/FindNext → обязательно используй FindFirst(FixLongPath(путь + '\*.*'), faAnyFile, SR).
